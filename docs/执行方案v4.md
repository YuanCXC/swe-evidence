# Gather, Combine, or Skip：证据交互感知的软件修复证据获取方案

## 一、项目目标与基本原则

本项目研究：

> 在有限预算下，软件修复 agent 应该读取哪些仓库证据、哪些证据必须组合、哪些证据可以相互替代，以及何时停止继续探索。

项目包含三个核心贡献：

1. 面向修复保障度的证据获取任务；
2. Evidence Sufficiency Value-of-Information Policy；
3. 证据互补、替代与冗余感知建模。

本项目的终点是形成证据包并判断其是否充分，不生成补丁、不修改代码、不运行测试，也不以实际修复结果作为标签或评测依据。

核心定义为：

\[
S(K)=P\bigl(C(K)=1\mid q,K\bigr)
\]

其中：

* \(q\) 为问题描述；
* \(K\) 为当前证据集合；
* \(C(K)=1\) 表示证据包已经覆盖形成正确修复判断所需的关键信息；
* \(S(K)\) 为证据充分性价值，也称修复保障度。

这里的“保障”是证据信息层面的充分性判断：证据包应覆盖故障位置、故障机理、预期行为、相关约束和影响边界，并且不存在未解决的关键证据缺口。它不表示项目已经生成、执行或验证了某个修复。

候选证据的条件边际价值为：

\[
\Delta(u\mid K)=S(K\cup\{u\})-S(K)
\]

成本调整后的净价值为：

\[
Q(u\mid K)=\Delta(u\mid K)-\lambda\operatorname{Cost}(u)
\]

证据交互值为：

\[
I(u,v\mid K)
=S(K\cup\{u,v\})-S(K\cup\{u\})-S(K\cup\{v\})+S(K)
\]

当 \(I>0\) 时，两条证据表现为互补；当加入 \(u\) 后 \(v\) 的边际收益显著衰减时，\(u\) 对 \(v\) 具有替代作用。最终停止条件由当前充分性、关键缺口覆盖情况与剩余候选的净收益共同决定，而不是训练一个与充分性定义割裂的 STOP 分类器。

整个项目必须遵循以下原则：

* 所有模型可见代码均来自修复前 `base_commit`；
* 可以读取仓库中已有的测试代码和测试断言，并将其作为证据，但禁止执行测试；
* Gold patch、test patch 和外部 gold context 只用于离线构造监督标签，禁止进入模型输入；
* 项目不生成补丁、不修改代码、不调用修复器，也不运行测试或验证实际修复结果；
* 外部数据只提供上下文、位置、约束或轨迹弱监督，不直接等同于证据充分性；
* \(S\)、\(\Delta\)、\(I\) 和 STOP 标签以证据需求覆盖与充分性判定为准；
* 大模型只处理程序规则和现成数据无法解决的歧义样本。

## 二、网络与论文数据盘点

### 2.1 第一优先级：直接接入的核心数据

| 数据源                     | 可直接利用的内容                                                               | 在项目中的角色                           | 是否减少 LLM 标注 |
| ----------------------- | ---------------------------------------------------------------------- | --------------------------------- | ----------- |
| SWE-bench               | issue、repo、base commit、gold patch、test patch、FAIL_TO_PASS、PASS_TO_PASS | 任务、位置与约束弱监督，不执行其测试               | 是           |
| SWE-bench BM25 / Oracle | 官方预构造检索上下文                                                             | 检索基线、候选池诊断和上界分析                   | 是           |
| ContextBench            | 人工标注的文件与行级 gold context                                                | 上下文检索监督、span 映射、静态策略训练            | 显著减少        |
| SWE-Explore             | 成功修复轨迹提取的 core/optional regions、读取步骤和轨迹来源                              | 序列状态、探索轨迹、互补候选生成                  | 显著减少        |
| CORE-Bench              | issue-to-edit 和 broader-context 检索 qrels                               | Retriever 预训练和 broader-context 监督 | 显著减少        |

SWE-bench 官方数据提供 2,294 个完整实例和 500 个 Verified 实例，标准字段包括 `repo`、`base_commit`、`problem_statement`、`patch`、`test_patch`、`FAIL_TO_PASS` 和 `PASS_TO_PASS`。本项目只读取这些字段以构造任务、位置、预期行为和约束标签，不启动其执行环境，也不运行 `FAIL_TO_PASS` 或 `PASS_TO_PASS`。官方公开的 Oracle 及多个 token 预算下的 BM25 检索数据可作为静态检索基线。

ContextBench 报告了 1,136 个问题解决任务，覆盖 66 个仓库和八种语言，并为每个实例提供人工 gold context。其公开数据中的 `gold_context` 已包含文件路径、起止行号和对应内容，因此不应再调用大模型从 patch 猜测全部相关上下文。

SWE-Explore 包含 848 个 issue、203 个开源仓库和十种编程语言。每个实例包含 line-level core context、optional context、read-step provenance 和仓库快照信息；这些标签从多个成功修复轨迹中提取。发布仓库还提供了数据加载、仓库获取和评测代码。

CORE-Bench 面向 agentic coding 的代码检索，划分为代码理解、issue-to-edit localization 和 broader-context retrieval 三个层级，包含超过 18 万个查询和约 10.6 万个 broader-context relevance labels。它适合训练第一阶段 Retriever，但不能替代本项目的证据充分性标签。

CORE-Bench 必须固定为论文链接指向的 `zhangfw123/CORE-Bench`，避免误下载同名的科学复现实验 benchmark。当前 Hugging Face 页面还显示数据 viewer 存在 schema cast error，因此下载脚本必须采用文件级下载并进行本地 schema smoke test，不能依赖 viewer API。

### 2.2 第二优先级：结构和基线资产

#### Agentless

Agentless 将问题解决拆成 localization、repair 和 patch validation 三个阶段。本项目仅使用其 localization 与仓库预处理资产，不接入 repair 和 patch validation。可重点用于：

* 对比层级式文件/函数定位；
* 复用仓库结构生成逻辑；
* 生成独立于本方法的候选集合；
* 检查交互模型的提升是否仅来自更强 Retriever。

#### LocAgent

LocAgent 将仓库解析为有向异构图，适合复用或改造为 Evidence Interaction Graph 的结构底座。可重点复用：

* `contains`；
* `defines`；
* `imports`；
* `calls/called_by`；
* 文件、类、函数和变量之间的层级关系；
* 图上的多跳候选扩展。

LocAgent 官方仓库使用 Apache-2.0 许可证，并明确通过有向异构代码图表达结构与依赖。

### 2.3 第三优先级：预训练和轨迹学习数据

#### SWE-Gym

SWE-Gym 提供 2,438 个可执行 Python 软件工程任务，并公开部分成功 agent trajectories。其仓库集合与 SWE-bench 分离，本项目不执行这些任务，只提取可用于证据获取的读取与搜索轨迹，以预训练：

* read/search 等证据获取动作模式；
* 状态编码器；
* 工具调用成本模型；
* exploration loop 检测。

这些轨迹只能作为证据探索预训练数据，不能直接定义 \(S(K)\)。

#### SWE-smith

SWE-smith 自动向真实 Python 项目注入破坏已有测试的 bug，已生成约五万个实例，覆盖 128 个仓库，并公开任务、轨迹和生成流程。适合扩大以下弱监督：

* bug location；
* changed symbol；
* test-to-code relation；
* 证据获取 state/action 预训练；
* 不同证据预算下的读取轨迹。

其任务是合成 bug，因此不能直接与真实 issue 的证据交互分布混合评测。

#### Open-SWE-Traces

Open-SWE-Traces 报告了超过 20 万条、覆盖九种语言的 agent 轨迹，可用于训练通用 repository exploration encoder，尤其适合抽取读取、搜索、回退和重复探索模式。它只应进入预训练阶段，并必须进行任务、PR 和仓库级去重。

### 2.4 暂不作为核心数据的数据集

RepoBench、CodeSearchNet 和传统 docstring-to-code 数据可用于基础代码语义预训练，但与“给定 issue，在具体 repository snapshot 中检索多条修复证据”的目标存在明显差距。CORE-Bench 也指出，传统代码检索通常忽略真实开发请求中的多位置证据、局部干扰项和 broader context。

因此，这些传统数据只能作为初始化数据，不能成为主实验监督。

## 三、最终监督体系

项目采用四层监督，按可靠性递增。

### Tier 1：确定性程序监督

不调用大模型，直接从以下信息生成：

* Git diff；
* AST；
* Tree-sitter；
* symbol table；
* import graph；
* call graph；
* 数据流和状态读写；
* 测试导入和调用关系；
* span containment；
* 内容哈希和标准化代码哈希。

可生成：

```text
changed_file
changed_symbol
deleted_statement
contains
calls
called_by
imports
reads_state
writes_state
raises
handles
same_symbol
span_overlap
exact_duplicate
```

这些标签规模最大、成本最低，应优先完成。

### Tier 2：外部已有上下文监督

从 ContextBench、SWE-Explore、CORE-Bench 和 SWE-bench retrieval assets 导入：

```text
human_gold_context
trajectory_core_region
trajectory_optional_region
successful_read_step
edit_location
broader_context_qrel
bm25_context
oracle_context
```

这些标签主要训练：

* Retriever；
* span ranker；
* 静态 action policy；
* role coverage；
* 候选池召回。

### Tier 3：自动语义弱监督

只对程序规则无法确定的候选调用大模型，例如：

* 两个跨文件单元是否表达同一约束；
* 测试断言是否能够替代调用方源码；
* 两条证据是否各自提供独有信息；
* 文档描述与代码实现是否冲突；
* 两个候选是否必须联合解释 bug。

该层不能作为最终交互真值。

### Tier 4：证据充分性监督

先从 issue、Gold patch、test patch、已有测试代码、文档和结构关系中离线整理修复需求集合，再判断不同证据包对这些需求的覆盖情况。Gold patch 和 test patch 只存在于标签构造侧，其新增代码、精确修复表达和标签标识不得进入模型输入。

生成：

```text
requirement_coverage(K)
critical_deficit(K)
S(K)
Delta(u | K)
I(u, v | K)
Sub(u -> v | K)
STOP
```

确定性规则能够判定的样本直接生成标签；存在语义歧义的样本由受约束的 LLM 裁决，少量高价值样本进行人工复核。全程不生成补丁、不运行测试，也不使用实际修复成功率。

## 四、实例统一与数据泄漏控制

### 4.1 建立 Master Instance Registry

不同数据集可能包含同一 issue、PR 或 SWE-bench 实例。必须先统一实例身份，再划分训练测试集。

统一字段：

```json
{
  "canonical_instance_id": "...",
  "source_records": [],
  "repo": "owner/repo",
  "base_commit": "...",
  "issue_url": "...",
  "pr_url": "...",
  "original_instance_ids": [],
  "problem_statement_hash": "...",
  "patch_target_signature": "...",
  "task_group_id": "..."
}
```

匹配顺序：

```text
instance_id 精确匹配
→ issue/pr URL
→ repo + base_commit
→ repo + PR number
→ normalized problem hash
→ patch target signature
```

同一 issue、PR 或等价任务必须属于同一个 `task_group_id`。

### 4.2 推荐划分

#### Static Train

用于 Retriever 和静态策略训练：

* SWE-bench 官方训练实例；
* ContextBench 中未进入最终评测的任务；
* SWE-Explore 中未进入最终评测的任务；
* CORE-Bench train；
* 去重后的 SWE-Gym/SWE-smith 预训练样本。

#### Dev

用于：

* 成本权重 (\lambda)；
* STOP 阈值；
* 交互分类阈值；
* 候选池大小；
* packet 选择策略；
* checkpoint 选择。

#### Test-Retrieval

冻结一部分 ContextBench 与 SWE-Explore 实例，仅用于：

* gold span recall；
* core-region coverage；
* context precision；
* ranked budget evaluation。

#### Test-Sufficiency

冻结未进入训练数据的任务，只评估证据获取和充分性判断。优先采用：

1. repo-unseen 或 time-unseen 任务；
2. ContextBench 与 SWE-Explore 的冻结任务；
3. SWE-bench、SWE-bench Pro 或其他公开任务中能够离线构造修复需求标签的部分；
4. 自行构造的时间后移证据充分性评测集。

这里的 `Test` 表示数据集划分，不表示执行软件测试。评测只比较证据覆盖、充分性判断和获取成本。

### 4.3 三种必须为零的泄漏

```text
任务级泄漏：
同一 issue/PR 跨 train、dev、test。

代码级泄漏：
修复后代码、patch added lines 进入可见 evidence。

标签级泄漏：
gold context、core region 标记、修复需求标签或充分性标签进入 agent 输入。
```

## 六、Evidence Unit 构造

### 6.1 第一版强制支持的粒度

```text
file
class
function/method
branch
statement block
callsite
existing test
configuration section
documentation section
```

第一阶段不要生成全仓库语义摘要。摘要会产生大量模型调用，同时引入难以验证的语义噪声。

### 6.2 Unit Schema

```json
{
  "unit_id": "...",
  "canonical_instance_id": "...",
  "repo": "owner/repo",
  "base_commit": "...",
  "unit_type": "function",
  "file_path": "src/a.py",
  "symbol": "Class.method",
  "language": "python",
  "start_line": 30,
  "end_line": 57,
  "raw_content": "...",
  "normalized_content_hash": "...",
  "parent_unit_id": "...",
  "token_count": 280,
  "line_count": 28,
  "visibility": "visible",
  "provenance": "base_commit"
}
```

### 6.3 解析策略

```text
Python：
标准库 ast + tokenize

Java、JavaScript、TypeScript、Go、Rust 等：
Tree-sitter

解析失败：
ctags 或 line-window fallback
```

每个 unit 必须通过：

```text
git show <base_commit>:<file>
```

重新读取并计算内容哈希。外部数据中附带的代码内容只用于对齐，不能代替本地 commit 校验。

## 七、无需大模型的标签构造

### 7.1 Patch-to-Unit 映射

使用以下优先级：

```text
old_path 精确匹配
→ deleted line 精确匹配
→ hunk old range 与 AST span 重叠
→ section header 与 symbol 匹配
→ normalized token match
→ 父级 unit 回退
```

输出多值标签，而不是强制唯一位置：

```json
{
  "role": "buggy_logic",
  "canonical_unit_id": "statement-unit",
  "acceptable_unit_ids": [
    "statement-unit",
    "branch-unit",
    "function-unit"
  ],
  "mapping_method": "deleted_line_exact",
  "confidence": 1.0
}
```

### 7.2 外部 Span-to-Unit 映射

ContextBench 和 SWE-Explore 的 line span 使用：

[
Overlap(u,s)
============

\frac{|Lines(u)\cap Lines(s)|}{|Lines(s)|}
]

映射规则：

```text
Overlap = 1：
exact-contained

Overlap ≥ 0.8：
strong overlap

Overlap ≥ 0.5：
partial overlap

多个嵌套 unit 同时覆盖：
保存为 equivalence group
```

不要只选择最小 unit，否则可能人为偏向 statement-level 证据。

### 7.3 结构交互候选

#### 互补候选规则

```text
buggy logic ↔ caller
buggy logic ↔ callee
buggy logic ↔ related test
state writer ↔ state reader
exception source ↔ handler
producer ↔ consumer
configuration definition ↔ configuration use
return value ↔ downstream assertion
target symbol ↔ interface/implementation
```

#### 替代候选规则

```text
statement ↔ containing branch
branch ↔ containing function
同一 symbol 的高度重叠窗口
相同标准化内容的多个 unit
重复 assertion
函数体 ↔ 精确抽取的相关局部分支
同一约束的代码表达 ↔ 测试表达
```

最后一类语义替代关系只有在程序规则不足时才进入 LLM 裁决。

### 7.4 从成功轨迹生成交互候选

SWE-Explore 和其他公开轨迹可提供：

* 读取顺序；
* 多次成功轨迹共现；
* edit 前最近读取；
* 重复读取；
* 搜索后跳转关系。

可以定义静态共现分数：

[
CoRead(u,v)
===========

\frac{#\text{成功轨迹同时读取 }u,v}
{#\text{包含该任务的成功轨迹}}
]

但 `CoRead` 只能用于候选生成。

```text
共同出现
≠
充分性互补

先后读取
≠
因果依赖
```

## 八、最小化大模型标注的具体机制

### 8.1 不应调用大模型的任务

以下任务全部由程序完成：

```text
patch 解析
文件和行号定位
AST symbol 识别
span 映射
contains/calls/imports
代码重复检测
候选对枚举
外部标签导入
成本计算
确定性需求覆盖计算
STOP 标签计算
```

### 8.2 只有满足以下条件才调用大模型

候选对必须同时满足：

```text
结构规则无法确定
且
至少一个外部来源支持其相关性
且
模型训练确实需要该关系
且
当前标签不确定度高
```

建议只裁决：

```text
跨文件 complement
测试与代码是否表达同一约束
文档与实现是否重复
语义上不同但功能上可替代的 evidence
潜在 conflict
```

### 8.3 三级裁决漏斗

```text
第一级：
程序规则和外部数据直接决定

第二级：
本地小模型或开源代码模型判定

第三级：
仅对第二级不确定样本调用高成本模型
```

### 8.4 主动选择，而非全量标注

为每个候选对计算：

[
Priority(u,v)
=============

Uncertainty
\times
PotentialValue
\times
SourceDisagreement
]

仅对优先级最高的 5%～10% 进行语义裁决。

### 8.5 缓存键

```text
hash(
  issue_text
  + unit_u_hash
  + unit_v_hash
  + state_unit_hashes
  + prompt_version
  + model_version
)
```

相同输入不得重复调用。

### 8.6 自动验证

LLM 输出必须包含：

```json
{
  "relation": "complement",
  "shared_information": "...",
  "unique_information_u": "...",
  "unique_information_v": "...",
  "joint_information": "...",
  "quotes": [
    {"unit_id": "u", "quote": "..."},
    {"unit_id": "v", "quote": "..."}
  ],
  "confidence": 0.82
}
```

程序检查：

* quote 是否存在于原 unit；
* 是否引用了 patch added line；
* relation 是否属于允许集合；
* 交换 (u,v) 后 complement 判断是否大体一致；
* substitute 的方向是否被保留；
* 低一致性结果是否被标记为 `uncertain`。

## 十、证据充分性标签构造

### 10.1 构造修复需求集合

每个实例建立修复需求集合 \(\mathcal R\)，至少覆盖：

```text
fault_location：故障所在文件、符号或语句区域
fault_mechanism：现有逻辑为何产生问题
expected_behavior：正确行为或目标约束
dependency_constraint：调用方、被调用方、状态或配置约束
impact_boundary：修复可能影响的路径与兼容边界
```

需求来源包括 issue、Gold patch 的 old-side、test patch、已有测试代码、文档、调用关系和数据流。Gold patch 的 added lines 与 test patch 的精确修复表达只用于标签侧归纳，不得复制到 evidence unit、模型输入或缺口解释中。

### 10.2 基础状态

每个实例先建立少量公共状态：

```text
K0：issue only

K1：issue + top file evidence

K2：issue + file + target symbol

K3：issue + file + symbol + buggy logic

Kretrieval：
静态策略当前获取的 evidence packet
```

### 10.3 证据覆盖与集合充分性

为每个证据单元 \(u\) 标注其覆盖的需求：

```text
covers(u) ⊆ R
support_type：direct | structural | semantic
coverage_confidence：0～1
unique_information：该证据独有的信息
```

证据包 \(K\) 的充分性证书至少包含：

```json
{
  "covered_requirements": [],
  "critical_deficits": [],
  "conflicts": [],
  "sufficient": false,
  "sufficiency_score": 0.0,
  "certificate_source": "deterministic | llm_adjudicated | human_reviewed"
}
```

只有关键需求全部覆盖、证据之间不存在未解决冲突且没有关键缺口时，\(C(K)=1\)。概率形式的 \(S(K)\) 用于排序和校准，布尔证书用于最终充分性判断。

对于候选对 \((u,v)\)，分别判断：

```text
K
K + u
K + v
K + u + v
```

由此得到：

\[
\Delta(u\mid K)
\]

\[
\Delta(v\mid K)
\]

\[
\Delta(v\mid K\cup\{u\})
\]

\[
I(u,v\mid K)
\]

### 10.4 替代性定义

保留方向：

\[
Sub(u\rightarrow v\mid K)
=\Delta(v\mid K)-\Delta(v\mid K\cup\{u\})
\]

判定替代至少要求：

\[
\Delta(v\mid K)>\delta_v
\]

并且：

\[
\Delta(v\mid K\cup\{u\})<\epsilon
\]

这样可以排除“两条证据本来都无价值”的伪替代。


### 10.5 充分性标注 Pilot

标注量计算为：

\[
N_{\text{packets}}
=N_{\text{instances}}\times N_{\text{pairs}}\times 4
\]

第一轮建议：

```text
20 个实例
每实例 4 个候选对：
  2 complement candidates
  1 substitute candidate
  1 independent control
每个 pair 4 个 packet
```

总计：

[
20\times4\times4=320
]

先用 320 个证据包判断确认：

* 是否存在可观测的正边际价值；
* 是否存在正交互；
* 是否存在边际价值衰减；
* 需求集合能否覆盖正确修复所需的关键信息；
* 充分性证书在重复裁决中是否稳定；
* packet 格式是否真正限制了判断器可见证据。

Pilot 不通过时，不扩大充分性标签生成。

### 10.6 裁决一致性与校准

确定性覆盖规则保留完整推导链。需要语义裁决时，冻结提示词、模型版本和温度；对 Dev 与 Test-Sufficiency 中的高价值 packet 进行重复裁决或人工复核。

保存：

```text
requirement_count
covered_requirement_count
critical_deficit_count
conflict_count
sufficient_vote_count
insufficient_vote_count
review_agreement
```

充分性价值可用 Beta-Binomial 平滑：

\[
\hat S(K)=\frac{s+\alpha}{n+\alpha+\beta}
\]

同时保存可信区间和证书来源，避免将单次主观裁决错误解释为精确概率。

## 十四、推理流程

```python
K = []

while evidence_cost(K) < hard_budget:
    candidates = retriever.search(issue=q, state=K)

    sufficiency = policy.predict_sufficiency(q, K)
    critical_deficits = policy.predict_critical_deficits(q, K)

    scored = []
    for unit in candidates:
        delta = policy.predict_marginal_value(q, K, unit)
        net_value = delta - lambda_cost * evidence_cost(unit)
        scored.append((unit, net_value))

    best_unit, best_value = max(scored, key=lambda item: item[1])

    if not critical_deficits and sufficiency >= tau and best_value <= epsilon_q:
        break

    K.append(best_unit)

certificate = policy.build_sufficiency_certificate(issue=q, evidence=K)
```

推理终点是 `evidence=K` 与 `certificate`。系统不得继续生成补丁、编辑仓库或执行测试。

必须设置：

```text
最大 token
最大 evidence 数
最大轮数
最大 tool calls
```

即使 STOP 失效也不能无限探索。

## 十八、阶段验收门

### Gate 0：数据源可用

必须满足：

```text
数据可下载或已有本地镜像
revision 已冻结
文件哈希已记录
schema 已验证
许可证和发布限制已记录
```

CORE-Bench 等可选数据失败时允许跳过，不能阻塞 SWE-bench、ContextBench 和 SWE-Explore 主线。

### Gate 1：可信代码底座

```text
base_commit 可读取
外部 span 可映射
patch old-side 可映射
unit 内容哈希正确
修复后代码泄漏为 0
```

### Gate 2：静态 MVP

必须观察到：

```text
State-aware > Independent

Interaction-aware > State-aware

Substitute Duplication Rate 下降

Complement Candidate Recovery 提升

提升不是由读取更多 token 导致
```

未通过时不启动大规模充分性标签生成与端到端评测。

### Gate 3：充分性 Pilot

必须观察到：

```text
部分候选具有正 Delta

部分证据对具有正 I

部分候选加入已有证据后 Delta 衰减

不同 packet 的充分性结果并非完全相同

需求覆盖与充分性裁决具有可接受一致性

不存在补丁生成、代码修改或测试执行
```

### Gate 4：论文核心结果

最终至少支持：

```text
1. 相关性不能替代证据充分性价值；
2. 同一证据的价值依赖当前状态；
3. 部分证据必须联合获取；
4. 部分相关证据可以相互替代；
5. 交互感知策略减少冗余探索；
6. Adaptive STOP 改善 Sufficiency–Cost Pareto。
```

## 二十一、最终数据策略结论

项目不应从零开始让大模型标注所有 evidence。

正确的数据闭环是：

```text
SWE-bench
提供任务、patch、test patch 等离线标签信息
        ↓
ContextBench
提供人工 gold context
        ↓
SWE-Explore
提供成功探索轨迹和 line-level context
        ↓
CORE-Bench
提供大规模检索相关性监督
        ↓
AST / Tree-sitter / Graph
提供确定性结构关系
        ↓
确定性覆盖规则
生成修复需求覆盖关系
        ↓
少量 LLM / 人工复核
只裁决歧义语义关系与充分性
        ↓
Sufficiency Certificate Builder
产生 S、Delta、I 和 STOP 标签
```

现有数据可以替代绝大多数位置标注、上下文标注、读取轨迹标注和初始关系候选生成。项目真正需要自行生产、且最有研究价值的数据，是：

```text
不同证据集合和证据组合
对修复需求的覆盖差异，
以及这些证据是否足以保障后续形成正确修复判断。
```
