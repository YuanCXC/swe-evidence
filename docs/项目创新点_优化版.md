# Evidence Agent：项目创新点优化版

> **Gather, Combine, or Skip：面向软件修复上下文获取的状态感知、证据交互感知与自适应探索方法**

## 0. 项目边界与论文定位

本项目研究的是 **Evidence Acquisition / Context Acquisition（证据获取 / 上下文获取）**，而不是自动程序修复本身。

在线系统输入仅包括：

```text
SWE Issue / Problem Statement
+
Pre-fix Repository Snapshot
```

在线系统输出：

```text
Evidence Package
├── Selected Evidence Units
├── Relevant Symbols / Files
├── Structural Relations
├── Acquisition Trace
└── Sufficiency / STOP Decision
```

本项目明确 **不做**：

- 自动生成补丁；
- 自动修改仓库；
- 执行 Gold Patch；
- 运行测试或根据测试反馈继续修复；
- 用真实 patch 成功率作为训练标签或核心评价指标。

SWE-bench 已提供的 `patch` 和 `test_patch` 可以在 **离线监督构造与最终评价阶段** 作为参考修复信息使用，但不能进入在线 Agent、Retriever 或 Evidence Policy 的可见输入。

因此，论文的核心目标不是证明“系统能直接修好多少 bug”，而是证明：

> **系统能否在有限预算下，从修复前代码仓库中逐步收集到足以理解并支持已验证参考修复所需的关键信息，同时避免无效、替代和冗余证据。**

---

# 一、核心研究问题

项目最终研究的问题可以定义为：

> **在有限预算下，软件修复 Agent 应该收集哪些仓库证据、哪些证据需要组合使用、哪些证据可以相互替代，以及何时停止继续探索？**

传统代码检索主要优化：

```text
Issue 与代码片段的相关性
或
Gold location / Gold context 的召回率
```

但这并不能直接回答：

```text
当前已经知道这些信息以后，下一条最值得读取的证据是什么？
```

也不能处理：

```text
A 单独不够，B 单独也不够，但 A+B 足够；
A 与 B 都能表达同一约束，读取其中一个后另一个几乎没有增量价值；
当前证据已经充分，继续搜索只会增加成本和噪声。
```

因此，本项目把静态代码检索提升为一个 **状态条件化的序列证据获取问题**。

设：

- \(q\)：软件问题描述；
- \(K_t\)：第 \(t\) 轮已经获取的证据集合；
- \(C_t\)：当前在线可见候选；
- \(A_t\)：当前动作，允许为单证据、双证据或 `STOP`。

策略学习：

\[
A_t^* = \arg\max_{A \in C_t \cup \{\text{STOP}\}} f_\theta(q,K_t,A)
\]

项目真正关心的是：

> **Given what I already know, what should I acquire next, how should evidence be combined, and when should I stop?**

---

# 二、创新一：面向参考修复的证据充分性获取任务

## Reference-Grounded Evidence Sufficiency Acquisition

第一项创新不是简单扩大 Evidence 类型，而是改变证据获取任务的优化目标：

> **从“找到与 Issue 相关的代码”转向“获得足以支持已验证参考修复所需信息的证据包”。**

### 2.1 参考修复不是在线输入，而是离线评价参照

SWE-bench 提供：

```text
Problem Statement
Gold Patch
Test Patch
```

其中 Gold Patch 和 Test Patch 只用于离线监督或评价。

它们的作用不是告诉 Agent “答案是什么”，而是帮助评价器回答：

> **仅根据 Issue 与 Evidence Package，是否已经具备理解该参考修复为何需要这样修改的关键上下文？**

因此这里评价的不是：

```text
Evidence 是否直接包含补丁答案
```

而是：

```text
Evidence 是否覆盖理解参考修复所需要的故障位置、故障机理、预期行为、依赖/状态约束和修改影响边界。
```

同时必须明确：

> **Gold Patch 是数据集中已验证的参考修复，并不意味着它是唯一可能的正确修法。**

### 2.2 证据充分性定义

可以从 Issue、Gold Patch、Test Patch 以及可验证的结构信息中离线构造修复需求集合：

\[
\mathcal R = \{r_1,r_2,\ldots,r_m\}
\]

典型需求包括：

```text
fault_location
fault_mechanism
expected_behavior
dependency_context
state_flow
repair_scope
validation_constraint
```

定义当前证据集合的充分性：

\[
S(K) \in [0,1]
\]

它表示当前 Evidence Package 对关键修复需求的覆盖程度及关键缺口状态。

当：

```text
关键需求均已覆盖
+
不存在阻断性信息缺口
```

才允许把状态视为 sufficiently complete。

因此论文主目标可以写成：

\[
\max_\pi S(K_T) - \lambda\operatorname{Cost}(K_T)
\]

其中成本可以包括：

```text
Evidence tokens
代码行数
Evidence Unit 数量
Tool calls
探索轮数
上下文占用
```

### 2.3 这项创新解决什么问题

传统方法通常关注：

```text
Recall@K
Changed-location recall
Top-K relevance
```

本项目增加一个更接近上下文获取本质的问题：

> **找到了相关代码以后，证据是否已经足够？**

因此第一项正式贡献可以表述为：

> **提出面向参考修复约束的序列式证据充分性获取任务，在严格 pre-fix 和无 Gold 在线泄漏条件下，以有限成本获取充分而不过量的软件修复上下文。**

# 三、创新二：状态感知的证据边际价值策略

## Evidence Sufficiency Value-of-Information Policy

这是项目最核心的方法创新。

普通 reranker 学习：

\[
s(u\mid q)
\]

即候选 \(u\) 与问题 \(q\) 的相关性。

本项目学习：

\[
s(u\mid q,K)
\]

即：

> **已经知道 K 以后，候选 u 现在还有多少新增价值？**

### 3.1 状态价值

模型可以估计当前证据包的充分性：

\[
\hat S(K_t)
\]

它回答：

> 当前证据是否已经覆盖理解参考修复所需要的关键信息？

### 3.2 条件边际价值

候选证据 \(u\) 在当前状态下的增益定义为：

\[
\Delta(u\mid K_t)
=
S(K_t\cup\{u\})-S(K_t)
\]

因此，同一证据在不同状态下可以拥有不同价值。

例如：

```text
还没有目标函数时：
目标函数定义价值很高。

已经读过目标函数后：
同一函数的重叠窗口或摘要价值显著下降。

已经知道 buggy logic，但不知道调用约束时：
caller / test assertion / dependency 的价值上升。
```

这正是本项目区别于静态检索与静态 reranking 的关键。

### 3.3 成本敏感价值

进一步定义：

\[
Q(u\mid K_t)
=
\Delta(u\mid K_t)-\lambda\operatorname{Cost}(u)
\]

策略优先获取高边际价值、低成本的 Evidence。

### 3.4 自适应停止

`STOP` 与 Single / Pair 处在同一决策空间中。

理论上，当：

\[
\hat S(K_t) \ge \tau
\]

并且：

\[
\max_{u\in C_t} Q(u\mid K_t) \le 0
\]

则继续探索的净收益已经不足，可以停止。

实际实现中仍可以保留统一的 `STOP` 动作评分；上述条件用于解释和校准，而不是要求额外训练独立 STOP classifier。

因此第二项正式贡献可以表述为：

> **提出状态感知的 Evidence Sufficiency Value-of-Information Policy，根据当前已获得证据估计候选的条件边际价值，并在证据充分且继续探索不再具有正净收益时自适应停止。**

# 四、创新三：证据互补、替代与冗余感知

## Evidence Interaction-Aware Acquisition

软件修复证据并不是相互独立的代码片段。

不同证据之间可能存在：

```text
complement      互补
substitute      替代
redundant       冗余
independent     独立
conflict        冲突
```

### 4.1 证据互补性

两条证据单独价值有限，但组合以后能够覆盖新的关键需求。

定义交互价值：

\[
I(u,v\mid K)
=
S(K\cup\{u,v\})
-S(K\cup\{u\})
-S(K\cup\{v\})
+S(K)
\]

当：

\[
I(u,v\mid K)>0
\]

说明两条证据存在正互补。

典型场景：

```text
buggy logic + caller constraint
state writer + state reader
exception source + exception handler
target symbol + dependency behavior
implementation logic + existing test assertion
```

例如：

```text
证据 A：目标函数在空输入时直接返回缓存对象。
证据 B：调用方或测试要求空输入必须产生新的空对象。
```

单独 A 只能说明实现；单独 B 只能说明约束；A+B 才能完整解释现有行为为什么不满足要求。

### 4.2 证据替代性

如果：

\[
\Delta(v\mid K)>0
\]

但加入 \(u\) 后：

\[
\Delta(v\mid K\cup\{u\})\approx 0
\]

说明 \(u\) 已经覆盖了 \(v\) 的主要信息，二者具有替代关系。

典型场景：

```text
完整函数体 vs 对应 buggy branch
调用方源码 vs 已有测试对该行为的明确断言
重叠代码窗口
同一约束在代码与 docstring / test 中的重复表达
```

替代性不是简单文本相似度，而是 **信息功能相同**。

### 4.3 证据冗余

定义：

\[
R(u\mid K)
=
\Delta(u\mid\varnothing)-\Delta(u\mid K)
\]

当 \(R(u\mid K)\) 较高时，说明候选原本可能有价值，但当前状态已经覆盖了其主要信息。

这使 Agent 能够避免：

```text
重复读取同一函数的多个粒度
连续获取多个高度相似的调用点
重复获取表达同一约束的代码、测试或文档
```

### 4.4 Single / Pair / STOP 的作用

统一动作空间：

```text
[u]       单 Evidence
[u, v]    双 Evidence
STOP      停止
```

其中 Pair 不是简单为了增加候选数量，而是为“单条不足、组合充分”的互补 Evidence 提供显式动作表达。

第三项正式贡献可以表述为：

> **显式建模软件修复证据之间的互补、替代和冗余关系，使策略能够组合联合有效的跨位置证据，同时避免重复读取可替代上下文。**

# 五、系统层增强：状态自适应仓库探索

## State-Adaptive Repository Exploration

这一部分适合作为 **Agent / 系统层增强**，不建议包装成第四个核心理论创新。

普通多轮 Agent 往往使用固定流程：

```text
每一轮：
Retriever
+ Structure
+ Policy
```

更有研究意义的 Agent 设计是：

> **根据当前 Evidence State，动态决定下一步应该采用哪一种仓库探索方式。**

高层探索动作可以包括：

```text
global lexical/content retrieval
path / symbol retrieval
canonical structure expansion
caller / callee oriented exploration
local neighborhood expansion
STOP
```

其决策依据只能来自在线可见信息：

```text
Issue q
Current Evidence K
当前候选分布
预算状态
由 q + K 推断出的信息缺口
```

严禁直接读取：

```text
Gold Patch
Test Patch
Gold obligation
Witness group
Teacher answer
```

### 5.1 为什么这个 Agent 点值得做

它让 Agent 不只是回答：

> 下一条证据选哪个？

还回答：

> **下一步应该用什么方式继续探索仓库？**

例如：

```text
K = ∅
→ 优先全局文本/路径检索定位目标区域

已经获得目标函数
→ 转向结构邻居、caller/callee、相关符号

已经知道 buggy logic，但缺行为约束
→ 搜调用方、现有测试、约束相关代码

证据已经充分且剩余增益很低
→ STOP
```

### 5.2 保持“一个核心训练模型”原则

该探索路由不要求再训练第二套大模型。

可以采用：

```text
规则/状态机路由
基于 Policy score 分布的路由
由同一 Policy 提供辅助策略信号
```

因此：

> **Multi-Agent 是执行与调度框架，核心可训练 Evidence Policy 仍然保持一套参数。**

### 5.3 对应实验

```text
Fixed Orchestration
vs
State-Adaptive Exploration Routing
```

比较：

```text
Evidence Sufficiency Rate
Critical Requirement Coverage
Evidence Tokens
Tool Calls
Acquisition Steps
Redundant Evidence Rate
```

如果时间或工程资源不足，该模块可以作为增强项，不影响前三项核心创新成立。

# 六、证据交互图与监督构造

## 6.1 Evidence Interaction Graph

可以为每个实例建立 Evidence Interaction Graph。

节点为 Evidence Units：

```text
file
class
function / method
branch / local region
callsite
test assertion
configuration
documentation
```

边可以包括：

```text
complements
substitutes
supports
depends_on
contains
duplicates
conflicts_with
```

其中必须区分：

```text
deterministic structural edges
LLM-derived semantic candidate edges
sufficiency-calibrated interaction labels
```

不要把弱规则生成的边直接宣称为 Gold semantic relation。

## 6.2 结构规则弱监督

互补候选可以来自：

```text
changed symbol ↔ caller
buggy logic ↔ related condition
buggy logic ↔ existing test
field update ↔ field reader
target symbol ↔ called dependency
exception site ↔ exception handler
```

替代候选可以来自：

```text
statement ↔ containing branch
branch ↔ containing function
overlapping evidence windows
同一 symbol 的不同粒度上下文
重复表达同一约束的代码/测试/文档
```

这些规则用于生成高精度候选监督，不直接等价于最终充分性真值。

## 6.3 LLM 语义裁决

对于规则无法稳定决定的语义关系，可以使用受约束 LLM 判断：

```json
{
  "relation": "complement | substitute | independent | conflict",
  "shared_information": "...",
  "unique_information_u": "...",
  "unique_information_v": "...",
  "joint_information": "...",
  "source_quotes": [],
  "confidence": 0.84
}
```

要求：

```text
quote grounding
Evidence ID / span validation
输出 Schema 校验
多次判断或多 Judge 一致性检查
```

本项目不依赖多人专家人工复核作为正式实验前提。

# 七、参考答案引导的证据充分性评价

## Reference-Grounded Evidence Sufficiency Evaluation

这是项目在“不生成补丁、不执行测试”条件下最重要的评价设计之一。

### 7.1 在线与离线必须严格隔离

在线 Agent：

```text
Issue
+
Pre-fix Repository
        ↓
Evidence Agent
        ↓
Evidence Package K
```

离线评价器：

```text
Issue q
+
Evidence Package K
+
Gold Patch P
+
Test Patch T
        ↓
Reference-Grounded Judge
        ↓
Evidence Sufficiency Result
```

Gold Patch / Test Patch **只能在 Agent 完成后进入 evaluator**。

### 7.2 Judge 不判断“能否生成完全一致的补丁”

Judge 的问题应是：

> **Evidence 是否已经包含理解和支持该已验证参考修复所需的关键信息？**

建议拆成以下维度：

```text
Fault Location Sufficiency
Fault Mechanism Sufficiency
Expected Behavior Sufficiency
Dependency / State Context Sufficiency
Repair Scope Sufficiency
Critical Deficit
Overall Sufficiency
Redundancy
Conflict
```

最终可输出：

```text
Sufficient
Partially Sufficient
Insufficient
```

以及 0–4 或 0–1 的分项评分。

### 7.3 两条评价轨道

论文不应只依赖 LLM Judge。

**轨道 A：确定性 / 数据监督评价（主评价）**

```text
Gold Evidence Recall
Obligation Coverage
Witness Coverage
Action Hit@1
MRR / NDCG
STOP correctness
Premature STOP
Redundant / Substitute duplication
```

**轨道 B：参考修复引导的盲语义评价（补充评价）**

```text
Issue + Evidence + Gold Patch + Test Patch
→ Judge
→ semantic sufficiency
```

两条轨道结果共同支持“上下文是否充分”的结论。

### 7.4 不依赖人工审查的自动可靠性检查

为了验证 Judge 不是随意打分，可以设计自动扰动测试：

#### 关键证据删除

```text
Complete K
→ 删除关键 witness / key evidence
→ sufficiency 应显著下降
```

#### 无关证据注入

```text
K
→ 加入明显无关 Evidence
→ sufficiency 不应虚高，redundancy 应上升
```

#### 错配证据

```text
Issue A + Gold A
+
Evidence from unrelated Issue B
→ 应判为低充分性
```

#### 重复判断一致性

```text
同一输入重复 N 次
或
多个不同 Judge
→ 报告一致率 / 方差
```

这样可以在单人研究条件下构造可审计、可重复的语义充分性评价。

# 八、模型结构与训练目标建议

## 8.1 统一 Evidence Policy

项目仍建议只训练一个核心 Evidence Policy。

输入：

```text
q = problem statement
K = current evidence set
A = [u] | [u,v] | STOP
```

统一评分：

\[
s_A=f_\theta(q,K,A)
\]

Single、Pair、STOP 共用 Backbone 与排序空间。

## 8.2 集合状态编码

如果后续模型实现需要增强 Evidence Interaction，可以考虑：

\[
h_K = \operatorname{SetEncoder}(\{h_{u_1},\ldots,h_{u_t}\})
\]

并对候选与当前 Evidence Set 建模交互：

\[
h_{u,K}=\operatorname{Aggregate}(\{\operatorname{Interaction}(h_u,h_{u_i})\})
\]

最终预测：

\[
\hat\Delta(u\mid K)=f(h_q,h_K,h_u,h_{u,K})
\]

这属于模型增强建议，不应在未实现前写成已完成事实。

## 8.3 训练目标

可以采用统一排序损失，并按数据条件增加辅助目标：

\[
L
=
L_{\text{action}}
+
\lambda_v L_{\text{value}}
+
\lambda_i L_{\text{interaction}}
+
\lambda_s L_{\text{stop}}
+
\lambda_d L_{\text{deficit}}
\]

其中并非所有辅助项都必须实现。

最重要的是保持主任务清晰：

> **在给定 q 和当前 K 时，把真正具有新增充分性价值的 Single / Pair / STOP 动作排到前面。**

# 九、建议的关键实验

实验主线控制在“对比实验 + 消融实验 + 自动评价可靠性检查”，不扩展到真实修复执行。

## 9.1 整体方法对比

可比较：

```text
BM25 / lexical retrieval
Hybrid retrieval
Cross-Encoder reranker
Static Top-K context
Stateless scorer
State-aware scorer
Interaction-aware Evidence Policy
完整 Agentic rollout
```

指标：

```text
Gold Context Recall
Obligation / Witness Coverage
Evidence Sufficiency Rate
Critical Requirement Coverage
Mean Evidence Tokens
Average Acquisition Steps
Tool Calls
Premature STOP Rate
Late STOP Overhead
Redundant Evidence Rate
Substitute Duplication Rate
AUC-Sufficiency-Cost
```

## 9.2 状态感知消融

```text
Stateless: s(q,A)
vs
State-aware: s(q,K,A)
```

除了总体指标，还建议做受控分析：

> **固定同一个候选 Evidence，只改变当前 K，检查其排名/得分是否按预期变化。**

这能证明模型确实学习了“已有证据改变后续价值”，而不只是普通 reranker。

## 9.3 Pair / 互补证据消融

```text
Single-only
vs
Single + Pair
```

重点单独统计必须联合理解的样本：

```text
buggy logic + caller constraint
writer + reader
source + handler
target + dependency
implementation + behavioral constraint
```

避免仅用“Pair 搜索空间更大”解释提升。

## 9.4 STOP / 成本-充分性实验

```text
Fixed Top-K
Fixed rounds
Fixed token budget
vs
Adaptive STOP
```

核心结果不是单独的 STOP Accuracy，而是：

> **在相同充分性下减少 Evidence 成本，或在相同预算下提高充分性。**

建议画：

```text
X：Evidence Tokens / Tool Calls / Rounds
Y：Evidence Sufficiency / Requirement Coverage
```


# 十、三项正式核心贡献

论文贡献建议始终保持三项，不继续堆叠。

## 贡献一：序列式、参考修复约束的证据充分性获取任务

> **我们提出面向软件修复上下文的序列证据获取任务，在严格 pre-fix 和无 Gold 在线泄漏条件下，以参考修复所需信息为离线评价依据，在有限预算内获取充分而不过量的 Evidence Package。**

关键词：

```text
reference-grounded evidence sufficiency
budgeted acquisition
pre-fix repository
leakage-safe evaluation
```

## 贡献二：状态感知的证据边际价值策略

> **我们提出 Evidence Sufficiency Value-of-Information Policy，根据当前已获取证据估计候选 Single / Pair / STOP 动作的条件边际价值，使同一 Evidence 的价值能够随状态动态变化，并支持成本感知的自适应停止。**

核心：

\[
\Delta(u\mid K)=S(K\cup\{u\})-S(K)
\]

## 贡献三：证据互补与替代感知建模

> **我们显式建模证据之间的互补、替代和冗余关系，使策略能够发现单独不足但联合有用的跨位置 Evidence，同时避免重复读取信息等价或已被覆盖的上下文。**

核心：

\[
I(u,v\mid K)
=
S(K\cup\{u,v\})-S(K\cup\{u\})-S(K\cup\{v\})+S(K)
\]

Agent 的状态自适应探索路由作为系统层增强，不与这三项核心贡献争夺主线。

# 十一、推荐论文主张

中文摘要级表述：

> 现有仓库检索与代码上下文方法通常独立评估候选代码，难以表达“已有证据如何改变下一条证据的价值”，也缺乏对互补、替代与冗余证据的统一处理。我们将软件修复前的仓库阅读建模为一个有限预算下的序列证据充分性获取问题：系统根据当前已获取证据估计候选的条件边际价值，显式处理需要组合的 Evidence 与可替代上下文，并在关键修复信息已充分覆盖且继续探索不再具有正净收益时停止。系统仅输出 Evidence Package，不生成补丁或执行测试。评测阶段使用 SWE-bench 已验证的 Gold Patch 与 Test Patch 作为 evaluator-only 的参考修复信息，判断 Evidence 是否包含理解该参考修复所需的关键上下文，并与确定性 obligation / witness 指标进行交叉验证。

英文摘要级表述：

> Existing repository retrieval methods largely rank code evidence independently, overlooking that the value of a candidate depends on what has already been observed and that repair evidence can be complementary, substitutable, or redundant. We formulate software-repair context acquisition as a budgeted sequential evidence-sufficiency problem. Our state-aware evidence policy estimates the conditional marginal value of single, paired, and STOP actions, combines individually insufficient but jointly useful evidence, avoids substitutable context, and stops when critical information is sufficiently covered and further exploration is no longer cost-effective. The system ends with an evidence package rather than a generated patch. For evaluation, verified SWE-bench patches and test patches are used only by an offline reference-grounded evaluator to assess whether the acquired pre-fix evidence contains the information needed to understand and support the reference repair.

## **Gather, Combine, or Skip: Interaction-Aware Evidence Acquisition for Software Repair**


## **Evidence Sufficiency for State-Aware Repository Exploration**

## **State-Adaptive Evidence Acquisition for Software Repair Context**
